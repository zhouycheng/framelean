03 / 技术方案

Flutter + Rust Worker + FLL

Flutter 同时服务桌面和 Android 界面。Rust Worker 管理任务生命周期，FLL 封装媒体操作。通过独立进程把媒体执行故障限制在单个宿主内，使用同一套任务协议连接各类调用入口。

关闭与退出的语义

  • 关闭窗口：UI 退出，已提交任务继续。
  • 重新打开：连接既有 Worker，获取任务快照。
  • 正式退出：取消当前工作、暂停等待队列；发布阶段等待对账完成。
  • 宿主崩溃：当前任务失败可重试，队列和 UI 继续可用。
  • Worker 异常：受管宿主停止，重启对账；中断任务可从头重试。

实施中的四个重点

  • 解码器故障也可能发生在分析阶段，分析同样进入隔离宿主。
  • 先串行执行，再按实测扩展并发；进程隔离不能消除 CPU、内存和磁盘竞争。
  • 临时文件与目标位于同一文件系统，校验后发布；跨卷导出单独处理。
  • 发布验收检查动态库、ABI 和依赖实际加载，开发机可运行不足以证明安装包可用。

技术依据：Flutter 桌面支持 · Media3 Transformer · HandBrake 进程隔离。具体库版本与构建许可清单在依赖锁定时核验，本计划不提前宣称兼容。

03A / 设计依据与取舍

把当前链路推进为可扩展的媒体核心

以下为对照当前代码与归档经验形成的架构。P0 已建立真实处理链，P1 已有持久队列与发布恢复基础；本节模块、HTTP v4 协议及数据库 v2 已实现；P1 本机收尾及 P2 受控视频处理已有验收记录，后续能力继续按阶段推进。

  1. 媒体判断集中在 FLL。媒体事实、操作支持、特殊特征适配、完整执行方案和媒体结果校验使用同一套契约。Worker 保存这些结果并组织执行。
  2. 唯一任务状态在 Worker。数据库保存关键事实，协调器独占状态迁移；FLL 只管理一次操作的资源与进度，Host 只管理一次动态库调用。
  3. 选项来自完整方案。先生成满足输入、后端和保留要求的候选链，再投影成可选格式与预设。缺少处理步骤的候选不会出现在普通选择列表中。
  4. 单个动态库内按模块拆分。当前沿用一个 FLL crate、一个 libav 后端，支持三压缩预设及转封装/转码两条视频链。新增职责先形成清晰模块与测试，插件加载、独立规则引擎和通用工作流系统随实际需求演进。
  5. 重操作离开状态事务。分析、编码在 Host；哈希、文件检查和发布在 Worker 的受管 I/O 工作线程。数据库事务只保存已经准备好的数据与状态。
  6. 每次执行可追溯。任务保存不可变处理方案，重试新增执行记录；源文件、分析版本和执行能力发生变化时重新核验，保留已有历史。

03B / 媒体领域核心 · 压缩与转换已实现

FLL 内部：事实 → 候选 → 方案 → 执行 → 校验

FLL 是媒体领域能力的唯一实现入口。每个模块回答一个稳定问题，数据只向明确的下一层流动。对外保持 C ABI 与版本化 JSON；内部改用 Rust 结构体和枚举，避免任意 JSON 字段在执行链中流转。

api
外部如何调用？		版本化请求 → 操作句柄；poll → 操作阶段、结果或错误。只分派命令并管理一次调用。解析错误、未知版本和无效句柄明确返回；panic 边界不能替代 Host 的进程隔离。
source

analysis
媒体是什么？		来源、分析级别、可选缓存 → MediaFacts、读取警告。通过后端探测容器与全部轨道。基础分析不要求每条轨道都能解码；容器识别成功、字段未知、损坏和读取失败分别表达。
capabilities
这个构建能执行什么？		FLL 构建与实际后端探测 → CapabilitySnapshot。区分库原生支持、FLL 已接通、当前可初始化。只为已接通且通过样本验证的链声明执行资格；当前登记软件压缩、H.264 转封装和 HEVC 转 H.264 链。
adaptation
特殊特征改变哪些步骤？		事实、操作、保留策略、目标、能力 → 约束、适配步骤、排除原因。规则与实现集中组织，详见下一节。规则判断无数据库和全局状态；处理步骤通过统一 pipeline 执行。
planning
哪些选择可完成？		事实、能力、意图与选择 → AvailableChoices / ExecutionPlan。生成完整链，检查所有输入轨道去向、像素与色彩要求、时间戳策略、封装支持和后端可用性。预设参数在这里解析一次。
operations
压缩要达到什么结果？		压缩意图 / 已验证方案 → 操作约束 / 执行结果。压缩规定保持时长、显示尺寸与音轨语义；转换、分段等各自声明目标与校验要求。当前实现 compress 与 convert，未来分段操作复用事实和标准步骤。
pipeline
按什么步骤处理？		方案、输入、临时输出、资源额度 → 进度、已关闭的临时结果。按有序步骤执行读取、解码或直通、处理、编码、封装。先用固定步骤枚举与直接函数调用；通用 DAG 随实际需求引入。
backends
具体库怎样工作？		类型化步骤参数 → 原生操作结果、可分类错误。首批提取现有 libav RAII 与调用代码。库特有结构体止于后端边界；为新增后端按所需能力补充小接口。
validation
结果是否兑现方案？		输入事实、方案校验规则、已关闭输出 → ValidationReport。重开结果，检查容器、轨道映射、尺寸、时长、时间戳和方案要求的色彩/方向。验证通过后仍由 Worker 发布正式文件。

模块依赖与一次执行的资源边界

contracts 和 errors 不依赖其他模块；analysis 只取事实；planning 读取事实与能力并调用适配规则；pipeline 执行计划中明确列出的步骤；validation 读取同一份计划校验。任何模块都不能回调 Worker 修改任务状态。后端错误先映射为 FLL 错误，再由 Worker 关联 task_id / attempt_id。

一个 Host 承载一次 FLL 操作；FLL 可使用解码与编码所需线程，但必须遵守 Worker 传入的 ResourceGrant。首批给出明确线程上限，沿用软件编码基线；未能遵守的额度返回能力错误。内存估算属于建议值，硬内存隔离需要平台机制，不能把一个参数当成强制保证。

分析结束不代表整段视频无损坏

基础探测产出可用事实和局部警告。完整解码检查、关键帧索引、精确时间戳扫描作为后续有进度的深度分析。规划只依赖已取得的必要证据；运行中解码仍可能失败。

验证分级，证据可追溯

P1 保留全流程编码与输出重探测，补齐方案对应的轨道和时间戳检查；完整独立解码、播放和音画同步作为验收证据。ValidationReport 写明实际检查项目和容差，避免用“校验成功”代指未做的检查。

03C / 集中处理特殊媒体

适配层共享规则，核心操作组合步骤

以 adaptation/ 集中管理方向、色彩、时间、轨道、像素和特殊格式相关规则。每个特征目录包含规则、步骤实现入口与样本测试；不同核心操作按计划引用。首批将已有检查移入规则，并建立明确的“已支持 / 需补充事实 / 不可执行”结果。

规则决定是否需要一步处理、以及这一步的语义；后端负责具体媒体调用。相同旋转或时间基换算实现由步骤复用。新特殊格式需要新库时，在 backends 中适配库，在 formats 中登记识别、适配条件和可用步骤；其方案继续经过相同的执行与校验链。

特征族按操作决定处理方式首批范围与扩展门槛
方向与 SAR压缩需保持显示方向与显示比例；提取图片通常需把方向作用到像素；转封装需确认目标能保留相同方向语义。P1 先对旋转矩阵、非方形像素排除压缩候选。支持前同时验证“像素已旋转 / 仅保留元数据”，避免两者叠加产生双重旋转。
色彩、HDR、位深保留 HDR 需要完整色彩链；转 SDR 需要明确的色调映射步骤；8-bit 输出不能隐式承担 10-bit 保留承诺。首批 SDR yuv420p；HDR/BT.2020 按当前能力排除。后续显式提供“转换为 SDR”意图，并校验实际输出色彩描述与像素处理。
时间戳保留 time_base、PTS/DTS 顺序和音视频相对偏移；分段需把时间范围映射到源时间线。首批沿用现有时间戳基线并补 VFR/起始偏移样本。缺失或有歧义的时间戳进入诊断；修复策略验证后再开放对应候选。
多轨与附加数据每条输入轨道都必须有“复制 / 转码 / 显式舍弃”映射；每个操作声明哪些轨道属于输出目标。首批单视频 + 零/单 AAC 音轨。其他轨道保持可分析状态，压缩候选排除；避免只处理第一条轨道而遗失其余内容。
像素与尺寸编码器对像素格式、色度采样和尺寸的约束作用于整条链；补边/缩放产生明确输出效果。首批保持尺寸且为偶数 yuv420p。后续“补边”与“缩放”分别命名，校验最终显示尺寸和比例。
特殊格式先辨认媒体族与编码内容，再选择专用解码或桥接；转换后的中间信息仍进入统一事实与方案模型。按样本接入，不以文件后缀作为能力证据。新后端需通过输出语义、取消、内存释放及打包验证。

从规则到可选项的确定过程

  1. 以当前构建已接通的操作模板生成候选；当前支持 H.264 转码与 H.264 转封装，AAC 复制，输出 MP4/MKV。转封装保留原码流，同时解码检查视频完整性。
  2. 依据所有媒体特征运行规则，收集约束、必要事实和明确步骤。规则按版本固定；相互矛盾的约束产生排除原因。
  3. 校验步骤依赖和顺序。色彩变换必须发生在降位深与编码前；像素旋转方案必须同步处理方向元数据。多条规则影响同一属性时，规划器校验最终语义。
  4. 检查整条链的后端和保留要求。必要信息缺失时返回 needs_analysis；执行步骤尚未实现时排除候选。只有完全成立的链进入 available_choices。
  5. 用用户当前选择继续约束候选集合，再投影有效格式、预设及参数范围。排序只推荐已有效的候选，不能修改用户显式选择。
  6. 用户确定后生成不可变 ExecutionPlan，固定步骤、实际参数、规则版本和校验条件；execute 复核方案并消费这些参数。
“自动适配”的准入条件

保持用户目标语义、实现已验证、效果可描述且没有可见内容取舍时，可将必要适配包含在方案中。丢轨、裁切、缩放、HDR 转 SDR、音轨重混和有歧义的修复需要明确目标或显式选项。每个步骤都在计划中留痕，导出的结果可追溯。

线程与队列如何保持响应

网关线程仅接收请求、等待协调器回执或发送查询结果；协调器只执行短事务。Host 的读管道线程合并进度消息，并为终态保留位置。文件 I/O 使用有界工作队列，hash 循环设取消检查。各角色之间传递值对象和操作 ID，避免共享一个包含数据库与长任务的总锁。

工作通道P1 额度与顺序控制语义
媒体通道分析、执行及后续深度分析共用 1 个重操作槽位，持久 FIFO；一次只运行一个大文件工作。暂停队列阻止这些等待项启动，当前项继续。分析排在长转码后会等待，界面与 CLI 明确显示位置。
方案查询通道最多 1 个短时 Host，用已保存事实完成 capabilities/options/plan；结果按上下文缓存。此通道不得扫描整段媒体；所需事实不足时返回 needs_analysis。它可与重操作并行，避免选项查询等待整次编码结束。
文件核验与发布最多 1 个 I/O 工作；当前执行仍占用媒体槽位直到终态收敛。发布前核验可取消；进入 publishing 后完成对账再释放槽位。
控制与观察取消、暂停、退出消息优先处理；读查询分页，SSE 连接与缓冲有上限。关闭观察进程不会发取消。数据库提交延迟和系统资源竞争仍需真实压力测试，进程隔离不等同于性能隔离。

“磁盘可以并行几个任务”由 Worker 决定

FLL 返回方案的资源需求提示：CPU 工作类型、可用线程范围、估计内存、输入规模、读写类型以及输出空间估计是否可靠。Worker 结合当前任务、可用空间、系统负载和输出卷，决定是否启动及授予多少额度。CRF 输出大小可能未知，不能把估算当成空间保证。

P1 使用固定一个媒体槽位，检查目录可写与发布方式、剩余空间及运行中的写入失败。P3 再按实测制定 min(用户上限, CPU/内存预算, 存储预算) 的并发上限；卷标识不必然对应独立物理磁盘，无法确认拓扑时按共享存储保守限制。运行时短期资源不足进入等待原因，不改变媒体的可处理能力。

Host 管理的具体约定

  • Host 每次启动先检查包内路径、ABI、JSON 契约和构建版本。Host 动态库装载上限 30 秒、就绪后纯方案查询上限 10 秒，已通过包内冷启动验证；媒体总耗时不套用该超时。
  • 管道消息带 operation_id、attempt_id（执行时）、序号与类型。首批单帧上限 1 MiB；进度覆盖旧进度，终态单独保存。畸形、超限、重复终态或退出无终态归为协议/宿主错误。
  • 控制通道读取与 FLL 执行分离。取消先调用 fll_cancel，3 秒未结束则终止并 wait 回收 Host；控制通道 EOF 表示 Worker 消失，Host 停止，遗留文件交重启对账。
  • FLL 在读写中断回调、数据包/帧循环与校验循环检查取消。原生库无法及时返回时，进程终止提供上限；不会在仍有并发访问时释放 FLL 句柄或卸载库。
  • 日志关联 request_id / analysis_id / task_id / attempt_id，按大小轮换并限制总量。诊断导出隐藏凭据、真实账号路径和设备信息；私有运行数据保存在仓库外。

CLI 第一版的两条链路

直接处理

compress 文件 --output 目录

  1. 提交分析并等待基础事实，显示准备状态。
  2. 查询当前有效的预设与目标容器；由 FLL 生成方案。
  3. 整批预检查通过，提交任务并打印 task_id / attempt_id。
  4. 默认在任务入队后退出；加 --wait 才继续观察到终态。

“默认返回任务 ID”指准备完成、后台接受之后。准备期间退出 CLI，已提交分析继续，但尚未提交的压缩不会被自动创建。

显式查看与自动化

analyze → options → plan → compress

analyze 返回持久 analysis_id；其他 CLI 进程可查询结果。options 列有效配置；plan 展示实际输出参数与影响；compress 引用分析及选定预设提交。

tasks/task 查询，watch 观察，cancel 取消，retry 创建新尝试，task <id> --reconcile 重新核对发布结果，queue pause/resume 管理后续启动，doctor 与 worker start/stop 管理运行环境。

混合批次逐项显示分析结果；统一提交时任一项没有有效方案，整批不入队，用户可明确选择有效子集。任务执行后单项发生解码或源变化错误，队列继续处理下一项。退出观察或 Ctrl-C 不发送取消；正式取消使用 cancel，正式停止后台使用 worker stop。

CLI 的 --json 将机器结果写 stdout、进度和日志写 stderr；当前退出码约定：0 为接受成功或等待到成功，2 为参数/无可用方案，3 为 Worker/组件不可用，4 为等待到失败或中断，5 为等待到取消。默认异步提交的 0 不代表压缩已完成。

Flutter 与后续 Agent 复用同一结果

Flutter 只负责表单、媒体摘要、有效选项和任务投影；普通视图不展示被排除选项。CLI 补全与 MCP 工具的参数提示也使用这份结果。客户端不维护另一张格式或 HDR 兼容表。

数据类别保存位置复用与失效
媒体来源数据库路径和导入时间；路径是定位信息。同路径可被替换，不作为永久内容身份。首批按明确来源记录关联，不进行全库内容去重。

SourceStamp版本、文件身份、size、mtime、首尾样本摘要；小文件可全量摘要。首批采用首尾各 1 MiB，小于等于 2 MiB 全读。分析前后、执行打开时和结束时复核；读期间变化返回 source_changed。
可用选择当前按需查询，客户端缓存已显示的可用选择；Worker 侧查询缓存留作性能扩展。键为 facts_digest + capability_digest + rules/planner 版本 + 意图 + 已选条件；缺失重新计算。进程重启可重建，不成为历史事实。

校验与运行反馈validation_json 和终态摘要落库；百分比、速度与 ETA 仅内存。重启后旧进度失效，显示中断或待核对。估算信息不能覆盖已记录的实际结果。
深度分析产物后续：数据库存引用、参数、版本和指纹，大索引放受管目录。按任务需求生成。尚未接通的索引和理解结果不纳入 P1 数据迁移。

抽样指纹用于低开销发现常见替换与修改，不能证明文件全部字节未变；刻意保留大小、mtime 和首尾的中间修改可能漏检。执行仍重新打开并校验必要媒体条件。需要严格内容身份时增加完整哈希模式，并单独衡量大文件读取成本；本版不宣称彻底防止外部并发改写。

版本 1 → 2 的迁移策略

  1. 取得数据目录独占锁，使用 SQLite 一致性备份能力留存升级前数据库；以 user_version 和字段/索引/约束核对实际结构，异常时诊断并停止迁移。
  2. 在一个事务中新增版本、计划、取消、校验和发布身份字段；扩展 execution_attempt 状态约束与唯一索引。需要重建表时按依赖顺序复制并核验外键，提交时才提升 user_version。
  3. 旧事实标记为旧 schema，保留原 JSON；旧任务 plan_json 为空、preset_json 原样保留。历史成功记录和输出继续可查，不能把旧固定参数推测为已确认的新计划。
  4. 旧活动执行先按已有发布记录对账；缺少新计划的等待项记 interrupted / plan_required，队列暂停。用户重新分析与规划创建新任务，旧尝试继续留存。
  5. 校验旧库升级、空库建立、重复启动、事务中断回滚、未知版本、缺列/错约束和已有数据外键。禁止吞掉任意迁移异常或用清库解决启动失败。
把新增概念放到正确位置

数据库拥有持久 ID、关系与历史；FLL 产生可序列化事实和计划。FLL 不需要链接 SQLite，Host 不直接打开数据库，Flutter 与 CLI 通过 Worker 查询。规则调整先改变能力与方案版本，再决定是否补充分析，不用数据库列模拟每一种特殊格式。

03H / 状态与故障收敛

从接受请求，到可证明地交付结果

状态所有权与合法迁移

分析：queued → running → succeeded | failed | canceled | interrupted

执行主链：queued → running → validating → publishing → succeeded
等待 / 运行 / 校验 → failed / canceled / interrupted
发布 → succeeded / failed；重启后按证据进入 succeeded / interrupted / failed / reconciling
reconciling → succeeded / interrupted / failed（结果冲突）

cancel_requested_at：取消意图，不是“已经停止”的证明。
publishing / reconciling：取消返回结果正在完成或待核对，不进入 canceled。
task 展示状态 = 最新 attempt 的持久状态 + 当次内存进度/等待原因。

上图中 publishing 不接受取消；运行中错误进入 failed，Worker 消失后由恢复流程判定 interrupted。新增 reconciling 专门表示发布结果因外部卷不可用等原因暂时无法确认，不能伪装成仍在编码或直接宣布丢失。所有终态保持历史；重试创建新的 attempt。

迁移谁可以触发提交条件
创建 queuedCoordinator 处理 execute / retry。计划复核通过，task 与 attempt、顺序号、请求回执同事务写入；unique 约束保护同任务不重复启动。
queued → runningScheduler 提议，Coordinator 批准。暂停关闭、额度可用；条件更新并登记 temp_path；独占创建临时文件、保存 temp_identity 后才启动 Host。创建或启动失败按本次 attempt 记 failed。
running → validating有效 Host 阶段事件。operation_id 与当前 attempt 匹配；阶段只能向前。FLL 媒体校验后，Worker 的哈希与源复核也处在 validating。
validating → publishingPublisher 的准备结果。Host 正常退出、ValidationReport 通过、来源复核完成、文件摘要准备完毕；事务内再次检查取消意图后登记发布记录。
publishing → succeeded无覆盖发布成功，或恢复核验成功。正式文件与登记结果一致；output 与 attempt 同事务成功，随后通知观察者并清理临时名称。
终止为 canceled已持久化取消的等待项，或受管执行停止。Host 已退出 / I/O 已停止，没有正式发布；记录清理状态。收到取消请求时仅显示“取消中”。

流程一：正常压缩

  1. CLI / Flutter → Gateway：提交输入。协调器保存来源和 queued 分析并返回持久 analysis_id。
  2. Scheduler → Host → FLL：FLL 打开媒体、核对 SourceStamp、产出事实；协调器保存分析终态。客户端可退出，分析继续。
  3. 客户端 → 方案查询 Host：options 生成有效候选，plan 解析具体参数。客户端显示可选范围和结果影响。
  4. execute → FLL 重新核验：Worker 验证目录及来源的轻量文件观测，FLL 核对方案上下文；抽样指纹在实际执行打开时复核。整批通过后，协调器在一个事务中写入任务、方案、第一次执行与回执。
  5. Scheduler → Host：获得额度、登记临时输出并启动；FLL 用当前输入重新验证必要条件，按计划编码、封装、关闭并校验输出。
  6. Host → Coordinator → Publisher：保存校验报告；文件工作线程准备大小、哈希与身份，进入发布协议。
  7. Coordinator → Events：正式输出与终态持久化后发送 succeeded；客户端展示真实路径、体积变化、耗时与校验摘要。

流程二：取消、重试与同时到来的发布

cancel 命令先在事务内核对阶段，保存 cancel_requested_at 与请求回执，再向 Host 或 I/O 工作发信号。queued 项可直接取消；running / validating 项先显示取消中。协调器按同一顺序处理“申请 publishing”与“取消”：取消先提交则拒绝发布；publishing 先提交则取消返回 publishing，由发布完成状态收敛。

如果 Worker 在取消提交后、通知 Host 前崩溃，重启仍能读到取消意图，并在确认 Host 停止后完成取消与清理。前提是没有已进入 publishing 的记录。重试仅对 failed / canceled / interrupted 开放；源指纹或方案上下文变化时提示重新分析/规划，不在原任务中偷换参数。

3 秒强制停止适用于 Host。Worker 的文件哈希按块检查取消；操作系统阻塞 I/O 可能延迟停止，因此取消回执区分“请求已接受”与“执行已停止”。阻塞文件工作不能占住网关或数据库事务。

流程三：文件发布与崩溃恢复

步骤数据库动作文件动作与失败边界
1 · 准备attempt 已登记唯一 temp_path；媒体校验报告已保存。Worker 独占创建临时文件，Host 只写此路径。Host 关闭后，事务外计算大小/SHA-256、核对文件身份并刷写文件；此阶段可取消。
2 · 登记意图短事务检查未取消，写 output_artifact（目标路径、大小、哈希、文件身份），attempt 改 publishing。这时尚可没有正式文件。该记录是重启对账的依据。
3 · 发布重名时先更新本次目标路径，再重试创建；限制重试次数。沿用同文件系统硬链接、目标必须不存在的方式。竞争方先创建文件则重新命名，任何时候都不覆盖。目录同步能力按平台验证并记录。
4 · 记成功正式链接成功后，在同一事务中将 output 和 attempt 标 succeeded，更新 revision。数据库提交失败时保留正式和临时文件，等待恢复；不能报告成功或删除正式文件来“回滚”。

链接成功，数据库成功提交前崩溃正式文件身份、大小和哈希均匹配：补记 succeeded。补记成功后清理临时名称。新记录同时核对登记文件身份，避免把重名的另一份文件误认成本次发布。
正式路径存在但身份或内容不匹配failed / output_conflict，保留详细原因。保留该正式文件；禁止覆盖或自动删除。临时文件仍按本次所有权独立处理。
卷离线、权限变化，暂时无法核验reconciling，显示待核对并阻止同任务重试。保留文件记录；可重新执行 reconcile。其他任务由用户恢复队列后继续，避免把不可访问误判为丢失。
成功已提交，临时名称尚未清理保持 succeeded，继续清理。清理失败仅更新 cleanup_state；正式结果保持可查。

恢复先读取待处理记录，关闭读事务，再逐项执行文件 I/O，最后条件更新仍处于预期阶段的记录。新格式记录按文件身份与内容核对；旧发布记录沿用已有大小/哈希对账并保留 legacy 标识。清理限定为登记目录、登记文件名及可核对的归属。若在临时文件创建后、身份落库前崩溃，身份不明的遗留文件只记录诊断并保留，避免误删。

重连与启动 / 退出

持久状态与瞬时进度分开

revision 只在关键状态事务变化时递增；event_id = instance_id:seq 属于当前 Worker 会话。进度在内存合并，最多每 250 ms 推送一次；终态立即发送，空闲连接定时心跳。

snapshot 在协调器的一致性切点返回活动项、暂停状态、队列摘要、revision 与事件游标。客户端用该游标订阅后续事件；缓冲中缺失、实例变更或序号间断时重新获取快照。历史单独分页，旧百分比不能跨重启复活。

生命周期可观察

启动：数据锁 → 运行发现与诊断网关 → 版本检查 / 迁移 → recovering 对账 → ready 或 degraded。恢复结束前关闭调度；有遗留等待项的重启保持暂停，由用户继续。首次空库没有恢复项时可直接就绪。数据库无法打开时提供健康诊断，阻止任务提交。

正式退出：拒绝新写命令 → 持久暂停 → 取消未发布工作 → 等待当前发布完成或保存待核对记录 → 清理受管进程 → 移除 endpoint。已持久化的 reconciling 可留待下次启动，不必等离线卷重新连接；未停止的 I/O 仍显示退出处理中。等待中的任务保留，关窗/退出观察只断开客户端。

Host 崩溃只使当前操作失败；单项输出冲突不会破坏历史。数据库写失败、组件不可用等系统性故障让 Worker 进入 degraded 并暂停新启动，防止所有等待任务被依次消耗成失败。恢复后的重试由明确命令触发，不自动生成无穷重试。
